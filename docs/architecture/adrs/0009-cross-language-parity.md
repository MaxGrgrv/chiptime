# ADR-0009: The cross-language parity contract (Python ↔ TypeScript)

> Status: ACCEPTED · 2026-08-21 · Feature: F31 (M3)

## Context

ADR-0001 made the corpus, not the code, the contract between implementations. ADR-0002 made
canonical JSON byte-identical by construction. Both were written *for* M3 and neither has been
exercised by a second implementation yet.

Porting ~9,000 lines of Python to TypeScript surfaces divergences that "produce the same JSON"
does not by itself pin down: how numbers round, how 64-bit values survive, what a `Date` prints,
which library computes `sin`, and what the public API is even called. This ADR fixes those, so
that "parity" is a testable property rather than an intention.

## Decision

### 1. The corpus is the gate; everything else is a means to pass it

The TypeScript conformance runner is a direct port of `python/tests/conformance/test_corpus.py`:
for every case in `corpus/MANIFEST.json` (and `corpus/private/MANIFEST.json` where present) it
asserts the `input.fit` sha256, byte-identical `expected.json` in lenient mode, the graded
outcome per mode, the strict-mode raise code, and double-parse determinism. **`expected.json` is
never regenerated to make TypeScript pass.** A divergence is a TypeScript bug until proven to be
a Python bug, and if it is a Python bug it is fixed in Python first, in its own commit, with the
snapshot regenerated by `gen_all.py --expected`.

### 2. Public API: idiomatic camelCase; wire format untouched

The JSON is the contract, the API is ergonomics. Canonical output keys, error codes, provenance
codes, diagnostic codes, CLI flags, and exit codes are **identical strings** in both languages.
The TypeScript *call surface* is camelCase:

| Python | TypeScript |
|---|---|
| `chiptime.parse(src, mode=..., strip_pii=..., include_unknown=..., include_raw=...)` | `parse(src, { mode, stripPii, includeUnknown, includeRaw })` |
| `iter_messages` / `iter_frames` | `iterMessages` / `iterFrames` (generators) |
| `result.to_canonical_json() -> bytes` | `result.toCanonicalJson(): Uint8Array` |
| `result.to_dict() -> dict` | `result.toJSON(): unknown` |
| `result.file_type` | `result.fileType` |
| `records.stream(name)` / `.streams()` / `.rows()` | same names |
| `FitError(code, detail, byte_offset, suggestion)` | `FitError extends Error` with `code`, `detail`, `byteOffset`, `suggestion` |

A name-mapping table lives in the migration guide and is checked by `/doc-check`. Snake_case
aliases are **not** exported: one name per concept.

### 3. Number kernel: Python semantics, ported explicitly

JavaScript's built-ins do not match Python's, and several of these values land in canonical
output. `js/src/numeric.ts` provides the following, and **`Math.round` is banned by lint** in
`js/src`:

- `pyRound(x)` — round-half-to-even, matching Python's `round(x)`. `Math.round` is half-up and
  disagrees on every `.5`, and on `-0.5` (Python `0`, JS `-0`).
- `pyRoundN(x, n)` — Python's `round(x, n)`, which rounds on the shortest decimal representation.
  Naïve `Math.round(x * 10 ** n) / 10 ** n` diverges (`round(2.675, 2)` is `2.67`, not `2.68`).
- `median(xs)`, `mean(xs)` — `statistics` semantics.
- `pstdev(xs)` — CPython ≥ 3.8 computes this over exact rationals (`Fraction`) and rounds once
  at the end. A float-accumulating port diverges in the last ULP, which can flip an interval
  classification. Ported using the same exact-rational reduction over `BigInt`.

Summation order is part of the contract: any accumulation feeding output iterates in the same
order in both languages.

### 4. 64-bit values: `BigInt`, then the ADR-0002 string policy

`uint64` / `sint64` base types and the `uint64z` variants decode into `BigInt`, not `number`.
The shaping layer applies the existing rule unchanged: magnitudes beyond 2^53 − 1 serialize as
decimal strings, everything else as JSON numbers. The canonicalizer refuses an out-of-range
`number` in both languages (bug guard, ADR-0002 §2).

### 5. Timestamps: the integer formatter, never `Date`

`Date.prototype.toISOString()` always emits milliseconds (`…T00:00:00.000Z`); Python's
`strftime("%Y-%m-%dT%H:%M:%SZ")` does not. The TypeScript port uses the same Hinnant
`civilFromUnix` integer algorithm as `decode.py`, and the semantic model stores FIT seconds
plus a formatter — **`Date` never appears on an output path.** It may appear in public API
return types as a convenience, computed from the same integer.

### 6. Transcendental math: bounded, gated, and honest about it

`semantics/plausibility.py` uses `sin`/`cos`/`asin`/`sqrt` (haversine) on the *core* path, and
`metrics/load.py` uses `exp`. `sqrt` is correctly rounded by IEEE-754 in both languages; the
others are not, and V8's implementations are not bit-identical to any libm. Python's own
cross-OS determinism already rests on the same assumption (macOS and Linux libm differ in
principle and the corpus passes anyway) because every value derived from them is thresholded or
rounded to 1–4 decimal places before it reaches output.

The decision is to **keep the same formulation and let the corpus gate it**, not to build a
fixed-point trig kernel for a hazard that rounding already absorbs. Concretely:

- No new transcendental call may be introduced on a canonical-output path in either language.
- Values derived from one are rounded (`pyRoundN`) before entering output — already true today.
- If a corpus case ever flips, the fix is to widen the rounding at that site, not to regenerate
  the snapshot; if that proves insufficient, this ADR is superseded by a shared math kernel.

### 7. Zero runtime dependencies, in both languages

The Python core has none; the npm package has none either. This is why zip/gzip unwrapping ships
as an internal inflate (`js/src/inflate.ts`) rather than `node:zlib` or `DecompressionStream`:
it keeps `parse()` **synchronous and identical** in Node, browsers, Deno and Bun, with no
runtime branching and no async infection of an API that is synchronous in Python. Dev
dependencies (TypeScript, vitest, Biome) are unconstrained.

### 8. Profile tables have one source and two emitters

`scripts/generate_profile.py` gains a TypeScript emitter and writes both
`python/src/chiptime/profile/generated.py` and `js/src/profile/generated.ts` from the same
locally-downloaded SDK profile, in the same run. Neither file is hand-edited; the SDK material is
still never committed (ADR-0004). `scripts/check_profile_parity.py` normalizes both tables to a
canonical digest and requires equality — CI fails if they drift.

### 9. Versioning: mirrored minors, independent patches, lockstep after parity

npm `0.N.0` denotes the feature surface of PyPI `0.N.0`. Patch releases are independent.
Python `0.3.0` (M2.5) and the M2.6 hardening were internal — the port inherits those behaviors,
so npm skips `0.3.0`. On reaching npm `0.7.0` the version lines merge: from then on a single
version number covers both packages and every feature bumps both together.

## Alternatives considered

- **Transliterate Python names into TypeScript** (`to_canonical_json`, `strip_pii`). One less
  mapping to maintain, but hostile to the ecosystem the package exists to serve; parity is a
  property of the bytes, not the identifiers.
- **`node:zlib` and a Node-only package.** Least code, but walks back the PRD's browser scope,
  and the browser fallback (`DecompressionStream`) is async — which would make `parse()` async in
  one runtime and not the other, the worst of both.
- **Shared fixed-point math kernel for trig/exp.** Guarantees bit-identity by construction, but
  is a substantial, slow, hard-to-audit module solving a hazard that rounding already absorbs and
  that the corpus would catch. Held in reserve (§6).
- **Generating TypeScript from the Python source** (transpilation). Attractive for parity, fatal
  for idiom and for the "each ecosystem gets a native-feeling API" decision in PRD §6.2.
- **A shared JSON profile artifact loaded by both.** Avoids the dual emitter, but costs a parse
  at import in both languages, breaks tree-shaking in the browser, and loses the typed constants
  that make the profile pleasant to work with.

## Consequences

- Parity is enforced by three CI gates, not by review: the TS conformance runner over the shared
  corpus, `check_profile_parity.py`, and a cross-implementation harness that diffs canonical bytes
  and CLI stdout between the two binaries for every case.
- `js/src/numeric.ts` is on the critical path for correctness and is covered by differential tests
  against Python over generated value sets, not only by unit vectors.
- Any future feature lands in Python first (corpus case + snapshot), then TypeScript. The corpus
  case is what makes the second implementation cheap.
- A Python behavior that is accidentally platform-dependent will now be *caught* rather than
  merely suspected — the second implementation is also a bug detector for the first.
